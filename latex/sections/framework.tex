The preceding sections derived two properties from the constraints of distributed deployment. Section~\ref{sec:membership} established that state synchronization in dynamic systems necessitates oracles with deletion support, formalizing this requirement as dynamic mutability in Definition~\ref{def:mutability}. Section~\ref{sec:cardinality} established that distributed aggregation without data shuffling necessitates oracles with composable merge operations, formalizing this requirement as algebraic composability in Definition~\ref{def:composability}. We observe that these properties address orthogonal constraints: mutability resolves the problem of maintaining oracle consistency with evolving datasets, while composability resolves the problem of combining partial results across network-separated partitions. This section analyzes the implications of this orthogonality for structure selection and deployment.

\subsection{The Mutability-Composability Orthogonality}
\label{subsec:core-properties}

Dynamic mutability addresses the constraint that distributed oracles must synchronize their state with datasets that undergo insertion and deletion. Algebraic composability addresses the constraint that distributed aggregation must combine partial estimates without transmitting raw data. These constraints are orthogonal in the sense that workloads can exhibit either constraint independently. A membership oracle for a dynamic dataset requires mutability regardless of whether the oracle is replicated or partitioned. A cardinality oracle for a static dataset requires composability if the dataset is partitioned, regardless of whether elements are ever deleted. The constraints impose requirements on different aspects of oracle functionality: mutability constrains the oracle's update interface, while composability constrains the oracle's merge interface.

We observe that the mechanisms enabling these properties impose conflicting design requirements on internal state representation. Mutability requires that the oracle retain sufficient information to identify and remove a specific element's contribution. The Cuckoo Filter achieves this by storing explicit fingerprints that can be located and erased (subsection~\ref{subsec:cuckoo-filters}). Each bucket contains fingerprints of elements mapped to that bucket, permitting targeted deletion by locating and removing the specified fingerprint. This explicit storage is the mechanism that enables constant-time deletion without false negatives.

Composability requires that the oracle's state be derivable from commutative operations applied to element representations. Such operations necessarily lose information about individual elements. The HyperLogLog sketch achieves this by retaining only maximum observables from each register, discarding element identities (subsection~\ref{subsec:hyperloglog}). The register-wise maximum operation used for sketch union cannot distinguish which specific elements contributed to a register's current value. This information loss is the mechanism that enables order-independent aggregation.

This information-theoretic tension explains the absence of structures that provide both properties optimally. A structure that retains sufficient information for targeted deletion (explicit element fingerprints) cannot perform order-independent aggregation, as the merge operation must track which elements have been processed to avoid double-counting. Conversely, a structure that performs order-independent aggregation (lossy compression to maximum observables) cannot support targeted deletion, as the information required to identify a specific element's contribution has been discarded. This reflects a trade-off between maintaining element-level granularity (required for deletion) and achieving compression through information loss (required for composable aggregation).

The consequences of this tension are examined in Section~\ref{sec:open-problems}, where we analyze the structural gap for workloads requiring both properties and evaluate hybrid system designs that maintain separate specialized oracles.

\subsection{Deployment Patterns and Property Requirements}
\label{subsec:patterns-from-properties}

The orthogonality established in subsection~\ref{subsec:core-properties} enables a classification of deployment patterns based on which constraint they address. We identify two pattern classes and derive the property requirements that enable each class.

\subsubsection{Local-Execution Patterns}
\label{subsubsec:mutability-copartition}

Distributed systems that align oracle partitioning with data partitioning enable local execution of oracle operations. A membership query for an element is routed to the node responsible for that element's partition, where both the data item and the oracle state are co-located. This eliminates network round-trips for oracle queries. The pattern applies to any workload where query routing can be determined from the queried element's hash value: membership testing in partitioned key-value stores, existence checks in distributed caches, and presence verification in content-addressable storage systems.

The viability of local-execution patterns is contingent upon oracle mutability. When data is deleted from a partition, the co-located oracle state must reflect this deletion to maintain consistency. Without deletion support, the oracle state diverges from the true partition contents. A query for a deleted element returns a false positive, forcing the system to perform a validation lookup against the backing data store. This validation lookup incurs the network round-trip cost that the oracle was designed to eliminate. As the deletion rate increases, the frequency of these wasted lookups increases proportionally, eventually negating the performance benefit of local execution.

The co-partitioning architecture (subsection~\ref{subsubsec:co-partitioning}) instantiates this pattern class for membership testing. Filter buckets are assigned to the same consistent hash ring as data keys. Each node maintains both the data items and the filter buckets within its assigned token range. Theorem~\ref{thm:co-partitioned-latency} establishes that expected query latency is independent of dataset size under uniform query distribution. This constant-time guarantee holds only for oracles that support deletion, as element removal must not require accessing non-local state or rebuilding global data structures.

The property requirement can be stated formally: a local-execution pattern is correct for dynamic datasets if and only if the oracle satisfies Definition~\ref{def:mutability}. The "if" direction follows from the Cuckoo Filter analysis in subsection~\ref{subsec:cuckoo-filters}, which demonstrates that deletion can be performed locally using only the element's fingerprint. The "only if" direction follows from the observation that any oracle lacking deletion support accumulates stale positives proportional to the deletion rate, forcing validation lookups that violate the local-execution guarantee.

\subsubsection{Hierarchical-Reduction Patterns}
\label{subsubsec:composability-hierarchy}

Distributed aggregation systems organize nodes into reduction hierarchies where intermediate nodes combine partial results from children. The pattern manifests in multiple system architectures. MapReduce implements two-level hierarchies: map workers produce partial results, reduce workers aggregate these results. Stream processing systems implement temporal hierarchies: window operators maintain sketches for time intervals, aggregator operators combine sketches across intervals. Multi-datacenter architectures implement spatial hierarchies: regional aggregators combine results from local data centers, global aggregators combine regional results.

The correctness of hierarchical reduction is contingent upon merge operation commutativity, associativity, and idempotency. Commutativity ensures that intermediate nodes can merge results from children in any order. This permits load-balancing strategies where faster children's results are processed immediately without waiting for slower children. Associativity ensures that the final result is independent of tree structure. This permits dynamic tree reconfiguration in response to node failures or load imbalances without affecting correctness. Idempotency enables fault tolerance under at-least-once delivery semantics. A child's result can be retransmitted and merged multiple times during network failures without corrupting the aggregate state.

The hierarchical aggregation architecture for cardinality estimation (subsection~\ref{subsubsec:hll-patterns}) instantiates this pattern class. Worker nodes construct HyperLogLog sketches over local data partitions. Intermediate aggregators merge sketches using the register-wise maximum operation. Theorem~\ref{thm:hll-union-properties} establishes that this operation is commutative, associative, and idempotent. Communication cost is $\Theta(ks)$ for $k$ worker nodes transmitting sketches of size $s$, independent of dataset cardinality $n$. This fixed-cost property transforms cardinality estimation from a communication-bound problem (exact counting requires $\Theta(kn)$ communication for data shuffling) to a computation-bound problem.

The property requirement can be stated formally: a hierarchical-reduction pattern produces correct global aggregates if and only if the oracle satisfies Definition~\ref{def:composability}. The "if" direction follows from the HyperLogLog analysis in subsection~\ref{subsec:hyperloglog}, which demonstrates that the union of partial sketches is equivalent to a sketch constructed over the complete dataset. The "only if" direction follows from the necessity of the three algebraic properties: without commutativity and associativity, the result depends on merge order; without idempotency, duplicate transmissions corrupt the aggregate.

\subsection{Structure Selection Criteria}
\label{subsec:decision-framework}

Structure selection is determined by analyzing two workload characteristics: data lifecycle dynamics and query result formation. These characteristics map directly to the property requirements derived in subsection~\ref{subsec:patterns-from-properties}.

\subsubsection{Data Lifecycle Dynamics}

Data lifecycle dynamics specify whether the system performs explicit deletion operations. Workloads fall into three categories:

\textit{Static datasets}: Elements are inserted once and never removed. Examples include append-only event logs, historical archives, and immutable data lakes. These workloads do not require mutability. A standard Bloom filter suffices for membership testing, as the oracle state never needs to remove elements.

\textit{Append-with-expiry datasets}: Elements are inserted with timestamps or time-to-live values and expire automatically. Examples include time-windowed stream analytics, session stores with automatic timeout, and caches with time-based eviction. These workloads can be implemented without explicit deletion by maintaining separate oracles per time window. When a window expires, the entire oracle is discarded rather than removing individual elements. This approach does not require mutability at the element level.

\textit{Fully-dynamic datasets}: Elements undergo arbitrary insertion and deletion operations driven by application logic. Examples include key-value stores with tombstones for deleted keys, caches with least-recently-used eviction policies, and distributed hash tables with explicit remove operations. These workloads require mutability. The oracle must support element-level deletion to maintain consistency with the dataset state.

\subsubsection{Query Result Formation}

Query result formation specifies whether results are computed by aggregating information from multiple partitions. Workloads fall into two categories:

\textit{Single-partition queries}: Each query is processed entirely within one partition. Examples include point lookups in co-partitioned systems (where routing directs queries to the responsible partition), range scans within a single shard, and membership tests in node-local caches. These workloads do not require composability. Each query is answered using only local oracle state.

\textit{Multi-partition aggregation}: Query results combine information from multiple partitions. Examples include global distinct counts computed from per-partition sketches, federated analytics aggregating statistics across administrative domains, and datacenter-level cardinality estimates derived from server-level estimates. These workloads require composability. The oracle must support merge operations that combine partial results into global results.

\subsubsection{Classification and Selection}

The intersection of data lifecycle dynamics and query result formation determines structure selection:

\textit{Fully-dynamic + Single-partition}: Workloads require mutability but not composability. The Cuckoo Filter (subsection~\ref{subsec:cuckoo-filters}) is the exemplar structure. Application contexts include membership testing in partitioned key-value stores where each query targets a specific partition, filters for LSM-tree SSTables that undergo compaction and tombstone removal, and Pending Interest Tables in named-data networking where interests expire upon data retrieval.

\textit{Static or Append-with-expiry + Multi-partition}: Workloads require composability but not mutability. The HyperLogLog sketch (subsection~\ref{subsec:hyperloglog}) is the exemplar structure. Application contexts include cardinality estimation in MapReduce batch jobs over immutable datasets, real-time analytics computing distinct counts over sliding time windows, and multi-datacenter monitoring aggregating metrics across geographic regions.

\textit{Fully-dynamic + Multi-partition}: Workloads require both mutability and composability. No single structure provides optimal performance for both properties, as demonstrated in subsection~\ref{subsec:core-properties}. This classification identifies a structural gap. Application contexts include distributed databases that must track element deletions for membership queries while aggregating cardinality estimates for query optimization, and distributed cache systems that must track cache invalidations while computing global hit rate statistics. The resolution strategies for this gap are examined in Section~\ref{sec:open-problems}.

\textit{Static + Single-partition}: Workloads require neither mutability nor composability. A standard Bloom filter suffices. This classification falls outside the scope of the framework, as the constraints that motivate probabilistic oracle deployment (state synchronization for dynamic data, distributed aggregation for partitioned data) do not apply.

This classification provides operational decision criteria. A system designer determines data lifecycle dynamics by examining whether the application logic includes explicit deletion operations beyond time-based expiry. Query result formation is determined by examining whether query execution accesses multiple partitions. The intersection of these determinations specifies the required properties and thus the appropriate structure class.
